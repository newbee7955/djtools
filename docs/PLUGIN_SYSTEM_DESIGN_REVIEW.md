# 豆角工具箱插件化架构设计评审

> 评审对象：[`PLUGIN_SYSTEM_DESIGN.md`](./PLUGIN_SYSTEM_DESIGN.md)  
> 评审日期：2026-09-09

## 1. 总体结论

整体方向正确，但当前版本更适合作为概念方案，还不适合直接作为开发规格。

方案已经覆盖了轻量宿主、按需安装、独立版本、远端注册表、完整性校验、失败回滚和共享重型依赖等核心方向。最需要补充或修正的是：

1. 插件 UI 与业务逻辑分别运行在哪个进程；
2. 插件的信任模型与权限如何真正执行；
3. Registry 和插件包如何证明发布者身份；
4. 更新、激活、失败恢复和运行中任务的生命周期；
5. 宿主与插件之间的 API 兼容策略；
6. 插件安装包、运行数据、缓存和共享依赖的版本管理。

如果直接按现有文档实施，最大的风险是：从远端下载的 JavaScript 代码可能获得宿主的全部能力，而 `permissions` 只是声明；同时，当前描述的“原子更新”和“零停机热重载”并未达到对应语义。

## 2. 现有方案中值得保留的部分

- 将高频变化的平台解析逻辑从宿主发布周期中拆出，问题定位准确。
- 宿主、插件、重型共享依赖的总体分层合理。
- 使用 manifest、Registry、SemVer、哈希校验和临时目录，已经具备更新系统的基本骨架。
- FFmpeg 等大体积组件按需安装，有助于减少首次下载体积。
- 先构建底座、再迁移业务、最后上线市场的阶段性思路基本合理。

这些内容可以保留，但需要在其下补齐安全边界和可执行的生命周期定义。

## 3. 必须优先修正的问题

### 3.1 插件运行位置没有定义清楚

原设计将 `dist/index.js` 同时标注为“插件前端入口 / 逻辑入口”。这会产生根本性的实现歧义。

当前抖音、B站模块并非纯前端代码，实际依赖：

- Node.js 文件系统和路径 API；
- Electron `app`、`BrowserWindow`、`session`；
- 本地 Cookie 和应用配置；
- FFmpeg 进程；
- 模块级下载任务和取消状态。

因此有三种不同结果：

- 放入普通渲染进程：因为没有 Node 权限，现有业务代码无法直接运行；
- 动态导入主进程：插件将拥有完整 Node/Electron 权限，且无法形成有效权限边界；
- UI 和主进程逻辑混成一个入口：构建、加载、卸载和热更新语义都无法稳定定义。

建议将入口显式拆分：

```json
{
  "entrypoints": {
    "ui": "dist/index.html"
  }
}
```

V1 建议不支持插件向主进程动态注入任意 Node.js 代码。插件包只包含：

- 沙箱内运行的 UI；
- 无权限、可重复执行的解析逻辑；
- 静态资源和声明式扩展信息。

网络、文件、Cookie、登录窗口、下载和 FFmpeg 均由宿主提供受控能力。

如果以后确实需要官方插件运行 Node.js 逻辑，可用 Electron `utilityProcess` 做崩溃和生命周期隔离。但 `utilityProcess` 仍然具有 Node 环境，只能视为进程隔离，不能替代权限沙箱。

参考：[Electron utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process)

### 3.2 `permissions` 目前无法形成权限边界

当前 preload 将完整的 `window.electronAPI` 暴露给整个主渲染页面。若插件 UI 作为 React 动态组件加载到同一个页面，它将自动获得所有已暴露的 API，无论 manifest 是否声明对应权限。

现有 API 中还包含以下敏感能力：

- `getConfig()` 会返回包含 B站、抖音 Cookie 的完整配置；
- `setConfig()` 可以修改全局应用配置；
- 文件、剪贴板和外部链接操作；
- 通用 API 请求能力；
- 所有平台解析和下载能力。

同时，目前 IPC handler 普遍没有验证调用者身份。这样一来，`permissions` 只能用于界面展示，不能阻止越权调用。

建议采用以下结构：

```text
可信宿主渲染层
└─ 插件市场、导航、容器布局

可信宿主主进程
├─ 插件管理器
├─ 权限代理 / 能力校验
├─ 下载任务管理器
├─ Cookie 与密钥管理
└─ FFmpeg 等共享服务
        ↕ 插件专属、会话绑定的 RPC
插件沙箱渲染进程
└─ UI + 无权限业务逻辑
```

每个插件建议运行在独立的 `WebContentsView` 中，并满足：

- `sandbox: true`；
- `nodeIntegration: false`；
- `contextIsolation: true`；
- 使用宿主管理的 preload，禁止插件包自带 preload；
- 不暴露原始 `ipcRenderer`；
- 不允许直接读取文件、Cookie 或完整配置；
- 不允许直接访问任意网络地址；
- 通过自定义协议加载插件资源，而不是直接使用 `file://`。

插件身份必须由宿主根据 `WebContents` 或已绑定的 `MessagePort` 确定，不能相信插件调用时自行传入的 `pluginId`。

参考：[Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)、[Electron Web Embeds](https://www.electronjs.org/docs/latest/tutorial/web-embeds)

### 3.3 当前宿主安全基线需要先补强

在加载远端下载的代码前，现有宿主还有几项需要先处理的安全问题：

1. 主窗口显式配置了 `sandbox: false`；
2. 主窗口的 `will-navigate` 逻辑允许导航到任意 HTTP/HTTPS 页面；
3. preload 会随主窗口页面加载并暴露宿主 API；
4. 当前 `<webview>` 使用了 `allowpopups: true`；
5. `shell.openExternal` 接受未经协议和域名约束的调用参数；
6. IPC handler 没有统一校验 `senderFrame`、参数类型和长度。

主窗口应只允许导航到宿主自定义协议；外部 HTTPS 链接应经过协议和域名校验后交给系统浏览器打开。所有特权 IPC 都应统一经过调用来源验证和参数 schema 校验。

### 3.4 SHA-256 不能证明插件来源可信

当前 Registry 给出 ZIP 的 SHA-256，只能证明下载结果与 Registry 中记录的摘要一致。如果 Registry 与 ZIP 同时被替换，攻击者也可以同时替换哈希值。

建议至少增加：

- 宿主内置可信发布公钥；
- Registry 或插件发布元数据使用数字签名；
- 签名内容覆盖插件 ID、版本、哈希、权限、平台、架构和发布时间；
- 元数据版本号和过期时间；
- 防止安装低于已知安全版本的回滚检查；
- 发布密钥轮换机制；
- 插件版本撤销和紧急禁用机制；
- 新版本增加权限时暂停自动激活，要求用户重新确认。

不一定需要完整实现 TUF，但可以借鉴其签名元数据、过期时间、防回滚和密钥轮换机制。

参考：[The Update Framework Specification](https://theupdateframework.github.io/specification/)

### 3.5 ZIP 解压缺少安全约束

插件 ZIP 在解压前和解压过程中必须防御：

- `../` 路径穿越和绝对路径；
- Windows 盘符、UNC 路径和保留设备名；
- 符号链接、硬链接和 Junction；
- 解压炸弹；
- 文件总数、单文件大小和解压总大小超限；
- 大小写不敏感文件系统中的重复路径；
- manifest 的 ID、版本与 Registry 不一致；
- 入口文件越过插件根目录；
- ZIP 中重复条目覆盖前一条目。

解压过程不得执行安装脚本，也不能信任压缩包中的 preload、原生模块或可执行文件。

### 3.6 当前描述的更新过程并不原子

原设计采用：

```text
旧目录重命名为 .bak
→ 新包直接解压到正式目录
→ 检查 manifest
→ 删除 .bak
```

这存在多个失败窗口：

- 旧目录改名后进程崩溃，正式目录不存在；
- 解压过程中崩溃，正式目录只包含部分文件；
- manifest 可读，但插件启动失败；
- 上一次失败遗留的 `.bak` 与新一次更新冲突；
- Windows 下正在使用或被安全软件扫描的文件无法重命名或删除；
- 删除旧版本后才发现新版本运行异常，无法快速回滚。

建议改成不可变版本目录：

```text
userData/
├─ plugins/<id>/versions/<version>/
├─ plugins/<id>/state.json
├─ plugin-data/<id>/
├─ cache/plugin-downloads/<id>/
└─ bin/<component>/<version>/<platform>-<arch>/
```

推荐更新流程：

```text
下载到 .part
→ 校验长度、哈希和签名
→ 解压到 staging
→ 校验所有文件、manifest 和兼容性
→ 移入不可变版本目录
→ 记录安装事务
→ 切换 activeVersion
→ 启动并完成健康检查
→ 保留 previousVersion
→ 后续再清理旧版本
```

应用启动时还应检查安装事务日志，并恢复被中断的下载、安装或激活流程。与其称为“目录原子替换”，更准确的表述是“可恢复的事务式安装与版本指针切换”。

### 3.7 “零停机热重载”承诺过度

重新挂载插件 UI，并不代表业务逻辑、下载任务和数据状态都已经安全切换到新版本。

当前代码中：

- B站和抖音的活动下载任务保存在模块级 `Map` 中；
- 下载取消句柄属于当前模块实例；
- 进度监听 API 没有返回取消订阅函数；
- 平台进度通过全局回调或向所有窗口广播；
- 新版本可能修改数据格式、权限或正在使用的解析逻辑。

如果直接热重载，可能发生：

- 正在下载的任务失去取消能力；
- 重复注册事件监听；
- 新旧版本处理同一任务；
- 新版本迁移数据后无法回滚；
- 正在使用的文件阻止更新目录清理。

建议把文档承诺调整为：

> 插件包可以后台下载。兼容的纯 UI 更新在插件空闲或下次打开时激活，无需重启宿主；运行中的任务继续由宿主任务管理器或创建该任务的旧插件版本完成。

需要补充以下生命周期接口：

- `activate()`；
- `deactivate()`；
- `dispose()`；
- 事件订阅返回 unsubscribe/dispose；
- 插件空闲状态判断；
- 激活健康检查；
- 崩溃计数、自动禁用和回滚。

如需真正无中断更新，应允许新旧插件版本短期并存，而不是覆盖当前版本目录。

## 4. 兼容性模型需要增强

### 4.1 `minAppVersion` 不足以描述兼容性

仅有最低宿主版本不能处理以下情况：

- 新宿主删除或改变旧 API；
- 插件只兼容某个宿主主版本；
- SDK 与宿主版本并非同步升级；
- Registry 最新版本不兼容当前宿主，但较旧版本可以兼容；
- 测试版、正式版和预发布版使用不同更新通道。

建议改为 SemVer 范围：

```json
{
  "schemaVersion": 1,
  "engines": {
    "doujiao": ">=0.2.0 <0.3.0",
    "pluginApi": "^1.0.0"
  }
}
```

宿主应尽量保证同一 `pluginApi` 主版本内向后兼容。破坏性变更通过新的 API 主版本发布，而不是仅依赖 `minAppVersion`。

原文“防止旧版本宿主升级后产生白屏或崩溃”应修改为“防止旧版本宿主加载不兼容插件后产生白屏或崩溃”。

### 4.2 Registry 不能只保存 `latestVersion`

如果最新版插件要求宿主 0.3，而用户仍在宿主 0.2，当前 Registry 无法告诉客户端应该安装哪个较旧的兼容版本。

Registry 应包含每个发布版本的不可变 artifact，例如：

```json
{
  "schemaVersion": 1,
  "plugins": [
    {
      "id": "douyin-downloader",
      "publisher": "doujiao-official",
      "name": "抖音下载器",
      "description": "...",
      "iconUrl": "...",
      "releases": [
        {
          "version": "1.2.0",
          "channel": "stable",
          "engines": {
            "doujiao": ">=0.2.0 <0.3.0",
            "pluginApi": "^1.0.0"
          },
          "artifacts": [
            {
              "platform": "win32",
              "arch": "x64",
              "url": "...",
              "size": 184320,
              "sha256": "...",
              "signature": "..."
            }
          ]
        }
      ]
    }
  ]
}
```

客户端应选择“当前通道中与宿主、API、操作系统和架构兼容的最高版本”，而不是直接比较一个全局 `latestVersion`。

### 4.3 插件市场元数据不完整

设计目标要求用户安装前看到图标、简介和能力说明，但当前 Registry 示例没有包含：

- 图标 URL；
- 描述；
- 权限清单；
- 发布者及签名身份；
- 支持的平台和架构；
- 主页、隐私说明或问题反馈地址；
- 每个版本的发布时间和兼容范围。

安装前展示的内容必须来自已经验证签名的 Registry 元数据，不能依赖尚未安装的 ZIP 包。

## 5. 权限建议改为结构化能力

类似下面的简单字符串：

```json
"permissions": ["network", "downloader", "browserView"]
```

粒度过粗。例如 `network` 如果意味着任意网络访问，插件可以向任意地址发送 Cookie 或本地数据。

建议改为带作用域的能力：

```json
{
  "permissions": [
    {
      "capability": "network.request",
      "hosts": ["www.douyin.com", "*.douyinvod.com"],
      "methods": ["GET", "POST"]
    },
    {
      "capability": "download.create",
      "destination": "user-selected"
    },
    {
      "capability": "browser.login",
      "hosts": ["www.douyin.com"]
    },
    {
      "capability": "media.merge"
    }
  ]
}
```

还需要区分：

- 安装时声明的权限；
- 用户已经授予的权限；
- 当前运行会话实际开放的能力；
- 新版本新增、删除或扩大作用域的权限。

插件不得直接获得原始 Cookie。更安全的方式是由宿主管理登录会话，并代表插件发出限定域名的请求。

`browserView` 也不适合作为权限名称，它把权限与 Electron 的具体实现类型绑定。建议使用 `browser.login`、`browser.navigate`、`browser.extract` 等业务能力名称。

## 6. 共享重型依赖需要版本协议

将 FFmpeg、yt-dlp 等放入共享池是合理方向，但不能假设所有插件永远兼容同一份“当前版本”。

建议插件声明宿主能力版本，而不是直接依赖二进制路径：

```json
{
  "requires": {
    "host.media.ffmpeg": ">=6 <8"
  }
}
```

宿主负责：

- 安装和验证二进制；
- 选择兼容版本；
- 校验平台与架构；
- 控制可用参数，防止命令注入；
- 管理并发、取消和进度；
- 处理许可证和组件更新；
- 必要时并存多个版本。

插件只调用结构化服务，例如 `mergeVideoAudio()`，不应获得可执行文件路径或任意命令行参数执行能力。

## 7. 插件数据和卸载语义需要定义

安装包、运行数据和缓存不应混放在同一个可替换目录中。

建议区分：

- `plugins/<id>/versions/`：只读、不可变安装包；
- `plugin-data/<id>/`：用户配置、业务状态；
- `cache/plugin-downloads/`：可安全删除的下载缓存；
- `logs/plugins/<id>/`：插件日志；
- `bin/`：宿主管理的共享组件。

卸载时默认只删除安装包，并明确询问是否同时删除插件数据。插件更新涉及数据迁移时，还需要：

- `dataSchemaVersion`；
- 幂等迁移；
- 迁移前备份；
- 迁移失败回滚；
- 新版本数据是否允许旧版本继续读取的兼容说明。

## 8. 构建产物规范需要更明确

“Vite/Rollup 单文件化”不能作为产物保证。动态 import、CSS、字体、Worker、WASM 和图片都可能生成独立文件。

建议定义可验证的包规范，而不是绑定某个构建工具：

- 所有文件必须列在构建产物清单中；
- 入口只能位于插件根目录内；
- 禁止运行时从未声明地址加载脚本；
- 使用严格 CSP；
- 产物不得包含安装脚本、原生模块和插件自带 preload；
- 源码映射是否发布需要明确；
- 单个文件和总包大小有限制；
- 包内容应可重复构建或至少可审计。

## 9. 安装体积目标需要用数据验证

原设计提出初次安装包“仅几十兆”，这个目标不能仅通过拆出抖音和 B站逻辑保证。

当前本地构建结果大致为：

- Windows 安装包约 160.8 MB；
- `ffmpeg.exe` 约 82.8 MB；
- 主渲染层仍包含 Monaco、Mermaid、KaTeX、语法高亮等较重依赖。

因此应先建立包体积分析基线，并明确哪些功能属于宿主核心、哪些也需要插件化。例如 Markdown、Monaco 编辑器和 Mermaid 如果继续留在宿主，移除下载器业务代码后的降幅可能低于预期。

建议将目标改成可验收指标：

- 纯净宿主安装包大小；
- 首次启动后的磁盘占用；
- 每个插件安装包和解压后大小；
- 首次打开插件的额外下载量；
- 宿主基础内存和单插件额外内存。

另外，“随主程序打包”不等于“常驻内存”，依赖表中的措辞建议改为“随宿主发布，运行时按需加载”。

## 10. 建议调整实施路线

现有 Roadmap 先开发插件管理器，再定义和验证插件运行模型，顺序存在风险。插件格式、安装目录和更新机制都会被运行时边界反向影响。

建议调整为：

### 阶段 0：确定边界和威胁模型

- 明确 V1 仅支持官方签名插件；
- 明确不支持任意主进程 Node 插件；
- 定义进程模型、权限模型和自定义协议；
- 定义 Plugin API 版本策略；
- 确定插件安装、数据和缓存目录。

### 阶段 1：制作本地运行时原型

- 使用本地固定插件包，不接远端市场；
- 创建沙箱插件容器和插件专属 SDK；
- 完成权限校验、生命周期和卸载清理；
- 先迁移一个插件的最小功能；
- 验证插件 UI 重载及宿主任务持续运行。

### 阶段 2：实现安全安装与版本管理

- 实现 staging、签名验证、不可变版本目录；
- 实现事务日志、启动恢复、健康检查和回滚；
- 实现兼容版本选择；
- 加入并发更新锁和幂等操作。

### 阶段 3：接入 Registry 和手动更新

- 建立签名 Registry；
- 支持缓存、超时、重试、代理和离线回退；
- 完成安装、升级、降级、禁用、卸载和清理数据；
- 展示发布者、权限差异和更新日志。

### 阶段 4：自动更新与正式插件市场

- 自动下载、空闲激活；
- 新增权限重新授权；
- 灰度发布、版本撤销和紧急禁用；
- 崩溃循环检测及自动回退；
- 完成从零安装的端到端验证。

## 11. 必须补充的测试

当前工程尚未定义自动化测试脚本。插件系统至少应覆盖：

- manifest 和 Registry schema 契约测试；
- 宿主与 Plugin API 兼容测试；
- 权限允许、拒绝和越权调用测试；
- IPC sender 伪造与非法参数测试；
- 恶意 ZIP、路径穿越和解压炸弹测试；
- 下载中断、磁盘满、哈希错误和签名错误；
- 安装每个阶段发生进程崩溃后的启动恢复；
- Windows 文件占用、杀毒软件扫描和目录改名失败；
- 新版本启动失败后的自动回滚；
- 更新期间仍在运行的下载任务；
- 重复激活、停用和事件监听清理；
- Registry 离线、超时、缓存过期和代理环境；
- 权限扩张时禁止静默激活；
- 旧宿主选择最高兼容插件版本。

## 12. 推荐的 V1 范围

第一版建议严格收敛为：

1. 只支持 Doujiao 官方签名插件；
2. 插件只运行在无 Node、开启沙箱的独立渲染进程；
3. 网络、Cookie、文件、下载和 FFmpeg 全部通过宿主能力代理；
4. 插件安装目录采用不可变版本结构；
5. 首期只做手动安装和更新；
6. 更新在插件空闲或下次打开时激活；
7. 运行中任务由宿主任务管理器持有；
8. 新增权限必须重新确认；
9. 先迁移一个插件验证完整链路，再迁移其余工具；
10. 自动更新和第三方插件生态后置。

## 13. 最终建议

这份设计的产品方向可以继续，但实施前应先补充“信任模型、运行时、权限、生命周期、兼容和供应链安全”六部分。

推荐的决策顺序是：

```text
先确定插件是否可信
→ 决定插件运行在哪个进程
→ 定义插件能调用哪些宿主能力
→ 定义 Plugin API 和生命周期
→ 定义包格式、签名和版本目录
→ 实现安装与恢复
→ 最后建设 Registry、市场和自动更新
```

按照这个顺序落地，可以避免插件管理器完成后，因为运行时边界不成立而大规模返工。
